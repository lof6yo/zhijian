# 纸见 v1.0.8

一个视觉版本：**把图标上的等高线搬到了应用背景上**，并给了五个真实地点各自的
颜色。强调色不再是独立设置项，而是跟着背景主题走。

## 背景换成一幅真实地形

原来是强调色染色 + 四个光斑的「光感」底。现在是一层**真实地形的等高线**：黄山、
龙脊、长白、沙海、呼伦贝尔，五个地点各一份。

真地形与「程序生成的纹路」的区别在密度本身：黄山的线在峰林处挤成一团、山脚处
散开；沙海的线是又长又平行的沙丘脊；长白是一圈圈闭合的火山口湖。这些形态没法
用噪声函数凑出来——凑出来的图看起来像等高线，但**没有一处是地形**。

几何在**构建期**从公开 DEM（AWS terrarium，zoom 12）提取：块平均 + `[1,2,1]/4`
高斯去噪，按目标层数反算等高距，`MIN_PATH_LEN=9` 剔除 DEM 噪声碎片，路径首点存
绝对坐标、其余存增量。运行期只读一份 10–30 KB 的纯文本，**不打包 DEM 位图、不
联网**——一个本地优先的笔记应用不该为了背景去取瓦片。

五份合计 109 KB，进 release HAP 后整个包从 1,345 KB 变成 **1,473 KB**。

### 为什么是竖幅而不是正方形

取样画布取 `448×758`，就是屏幕 `440×744` 的比例。正方形按 cover 缩放会横向裁掉
41% 的地形——山脊被切掉两侧，只剩下中间一条，读起来就不像一座山了。

### 为什么用 Canvas 而不是一堆 `Path`

沙海有 700 条折线、5628 个点。用 ArkUI 组件画就是一屏上千个节点，而它只是背景。
Canvas 是单个节点、一次性栅格化，整次重绘实测 **15 ms**。

描边按档位合并：**一档线一次 `stroke`**，所以 700 条折线只要 2 次描边。顺带一个
正确性上的好处——同一次 stroke 里重叠段按**并集覆盖率**栅格化，陡坡上挤在一起的
线不会叠成一块深色；逐条描边会。

## 五套主题，强调色由主题派生

| 地点 | 地形 | 底色 | 强调色 |
| --- | --- | --- | --- |
| 黄山 | 花岗岩峰林，密而陡 | 灰蓝 | 蓝 |
| 龙脊 | 梯田丘陵，舒展的同心弧 | 灰绿 | 绿 |
| 长白 | 火山口湖，一圈圈闭合 | 冷青灰 | 紫 |
| 沙海 | 沙丘脊线，平行而长 | 灰褐 | 橙 |
| 呼伦 | 草原缓坡，线很少很长 | 灰青 | 青 |

**强调色不再是独立设置项。** 设置页原来那行「强调色」三色块已经删掉，只剩
「背景主题」一行五个色点，每点画的是**它自己**那套配色（三层同心圆：选中环 +
底色圆 + 强调色圆点）。

留一个独立的色相开关会直接产生「沙海背景 + 黄山蓝按钮」这种组合——背景与前景
是两套不相干的色相，而「自动适配」也就成了一句做不到的承诺。派生关系写在
`ContourTheme.accentKey` 上（每个地点声明自己的色相），`Palette.indexOf(key)`
负责查表：**按 key 关联而不是按下标**，加第六个地点时不会把它静默指到别人家的
强调色上。

强调色从 3 套扩到 5 套，与五个地点一一对应。`Palette` 里三组没有读者的字段
（`glow*` / `page*` / `glass*`）整组删掉——留着它们，下次加主题就得凭空发明
十二个没人看的十六进制颜色值。

四个 `radialGradient` 光斑一并删除：它们压在等高线上会盖住线条，调淡到不盖住就
只是一层雾。底色保留原来的 160° 三段渐变（0.55 中点），只是色源从强调色换成
主题。

## 可读性：这一版唯一不能妥协的部分

背景是装饰，字是内容。所以定了一条硬预算，量的不是对比度比而是**感知亮度差**
（`0.299R + 0.587G + 0.114B`）——1.2 vp 的细线扎不扎眼取决于它和底色差几个灰阶，
比值在小字上会失真：

| | 浅色 | 深色 |
| --- | --- | --- |
| 普通线 ΔL | ≤ 16 | ≤ 14 |
| 计曲线 ΔL | ≤ 26 | ≤ 18 |
| 计曲线 / 普通线强度比 | ≥ 1.6 | ≥ 1.6 |

数值由 `tools/contour-budget.js` 按线上真实的合成公式逐主题验算，改一位十六进制
就非零退出；再由 `tools/contour-audit.js` 在**设备截图上**复核（按行取 95 分位估
底色，因为竖直方向有渐变——85 分位只在无渐变时成立）。

实测：

| | 浅色普通线 | 深色普通线 | 计曲线强度比 |
| --- | --- | --- | --- |
| 中位 | 13.6–14.0 | 11.9–13.3 | 1.74–1.87 |
| P90 | 24.4–25.7（计曲线） | 20.5–21.6（计曲线） | — |

**深色主题的计曲线必须比普通线更亮。** 这不是风格选择：深色底近黑，线越接近
底色就越弱，若计曲线取了更深的颜色，它反而变成弱的那一档，加粗也救不回来。浅色
相反，两套方向是反的，不能共用一张表。

顶部 130 vp、底部 110 vp 两条淡出带，让线给标题栏与页签栏让位。淡出用 Canvas 的
`destination-out` 擦 alpha，而不是盖一层底色——底色是渐变，同色遮罩对不上；擦
alpha 与底色无关，深浅共用一条遮罩。比例退到 6% 而不是 0：硬切会在带子边界留下
一道横线，比线还在更显眼。

## 一件已知但不在本轮范围内的事

切换深浅色时会有约 13 s 的卡顿（`ArkUINotifyConfigurationChange` 阻塞，
`THREAD_BLOCK_6S`）并被系统判为无响应。这次做了对照实验：关掉等高线层、回到
1.0.7 的构建重装，同一组操作仍在第 3 轮被杀——**是既有缺陷，不是等高线引入的**
（`ContourCanvas.redraw()` 实测 15 ms，不构成瓶颈）。留待后续版本单独处理。
